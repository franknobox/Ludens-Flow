# Ludens-Flow 后续开发计划 (Roadmap)

---

## 近期计划 (Near-term)

### 1. 常态化的稳定性、体验性优化
- **核心目标**：持续提升系统稳定性、状态流转一致性与整体可维护性，优先解决影响体验和可扩展性的基础问题。
- **具体方向**：
  - 持续验证 Prompt 分层、共享 schema 和结构化解析在真实项目中的稳定性，减少非结构化输出、协议漂移的问题。
  - 继续打磨工具调用提示词和上下文策略（重点），使工具使用、上下文和执行反馈更自然地融入 Agent 回复过程。
  - 持续优化前端外观、交互细节和结构分层，让工作台更好承接结构化结果、权限确认、文件上下文和工具过程展示。
  - 持续清理冗余代码、旧兼容链路和历史遗留实现，降低后续扩展成本。
  - 内部沉淀skills，做好演示流程；补全文案能力，持续优化github、mcp。
  - 做稳 Unity 工程文件读写、工程阅读与检索，并为高风险文件类型预留扩展位。
- **进度状态**：当前重点转向工作流灵活化、上下文策略、工具执行体验和真实场景下的提示词调优。

### 2. 工程执行闭环
- **核心目标**：让 Agent 从“给出建议”进一步走向“可控地执行工程任务”。
- **具体方向**：
  - 建立真正的任务执行循环，让 Agent 能围绕一个目标持续完成读取上下文、制定步骤、执行工具、观察结果和继续修正。
  - 完善 Patch / Diff 级编辑体验，展示将要修改和已经修改的文件、变更摘要、风险提示与确认结果。
  - 补齐命令执行与测试反馈能力，优先支持工作区内受控命令、测试/构建输出读取、失败原因回传与下一步建议。
  - 提升会话中的工作过程可见性，让用户能看到 Agent 正在搜索什么、读取什么、修改什么、运行什么，以及每一步的结果。
- **进度状态**：已有工作区读写、patch/delete、权限模式和工具事件基础；下一步重点是把它们串成稳定的端到端执行体验。

### 3. 更多引擎兼容与生态扩展 (Broader Engine Compatibility)
- **核心目标**：把 Ludens-Flow 从“默认偏 Unity 的游戏开发工作台”收敛为真正的多引擎游戏开发工作台，让 Unity、Godot、UE 等能力共享同一套项目、工作区、权限、工具和提示词模型。
- **具体方向**：
  - 保留 Unity 作为一个成熟能力分支，继续推进，同时让 Godot、Blender、UE 复用统一能力层，避免每个引擎长出一套彼此割裂的产品逻辑。
- **进度状态**：预期与工作流优化相结合，设定出更完善的引擎确定方式。

### 4. 游戏内模型能力接入（In-Game LLM Integration）
- **核心目标**：让开发者可以通过 Ludens-Flow 配置、测试、生成并导出面向游戏运行时的大模型能力，形成“工作台配置与测试 -> 游戏工程接入 -> 运行时调试与迭代”的闭环。
- **后续重点**：
  - 明确模块边界：Ludens-Flow 负责配置、测试、推荐、导出和接入指导，不承诺提供第三方模型 API 或替用户托管商业模型服务，避免用户误解能力范围。
  - 明确导出形态：当前以配置 JSON、接口约定、示例代码和接入说明为主，不强制绑定用户游戏工程的目录结构、网络层或运行时架构，也不把示例代码包装成必须采用的固定 SDK。
  - 将“导出说明”升级为“使用指南”，用零基础也能看懂的方式说明如何选择模型、填写密钥、配置场景、理解导出内容，并在 Unity / UE 等游戏工程中按需接入形成可运行的 AI 功能。
  - 优化“模型广场”：定位为模型推荐与快捷配置入口，点击模型后自动填入对应服务地址、模型名和推荐参数，用户只需要补充自己的 API Key 与项目侧配置。
  - 将自定义模型接入与模型路由能力打通，让用户可以把自有网关、私有模型或兼容 OpenAI API 的服务纳入统一路由、测试和导出流程。
  - 探索 Agent + MCP 自动落地路径：在用户授权后，让 Agent 读取游戏工程结构，选择合适位置写入配置和示例代码，并尝试跑通最小接入链路，但仍保留手动复制、手动调整和手动接入方式。
  - 优化界面浏览体验，重点改进场景配置、模型广场、自定义接入和使用指南之间的切换、信息层级、空状态、错误提示和深浅色适配。
  - 持续打磨实际使用体验，包括流式输出、工具调用审计、缓存、频率限制、成本预算、超时重试、降级策略和日志回传等真实游戏接入所需能力。
- **进度状态**：第一版“配置、测试、生成、导出”的可用闭环已完成并通过测试；下一阶段转向真实游戏工程接入验证与运行时调试回流。

## 远期规划 (Long-term Vision)

> 以下为探索性方向，不设硬性排期，将根据近期计划推进情况逐步展开。

### 5. Welcome 与启动体验丰富化 (Welcome & Onboarding Experience)
- **核心目标**：把当前轻量启动页扩展为更完整的产品入口，让用户在进入工作台前快速理解项目状态、配置完整度和下一步可做什么。
- **具体方向**：
  - 从单纯 Logo / 加载动画逐步扩展到首次使用引导、项目选择、配置检查、能力入口提示和 Demo 模式入口。
  - 在不打断熟练用户的前提下，为新用户提供模型配置、工作区权限、GitHub/Skills/MCP 等关键能力的状态提示。
  - 让 Welcome 页成为“进入工作台前的轻量总览”，而不是额外的登录或阻塞页面。

### 6. Agent 驱动的模块自动化 (Agent-Orchestrated Workbench Modules)
- **核心目标**：让工作台各功能模块不仅能被用户手动操作，也能被 Agent 以受控方式调用，形成“对话提出目标 -> Agent 选择模块 -> 执行配置/生成/导出 -> 回传工件”的自动化体验。
- **具体方向**：
  - 为文案加工、AIGC、MCP、GitHub、游戏 AI 配置中心、项目资料与设置等模块补齐可被 Agent 调用的能力接口、输入 schema、权限确认和结果事件。
  - 以文案生成 CSV 作为首批闭环：用户描述需求后，Agent 自动调用文案模块生成、校验并导出 CSV，同时保留手动入口。
  - 将外部 AIGC 能力纳入 Agent 调度链路，形成“在 Ludens-Flow 内选择能力 -> 跳转或调用外部 AIGC 服务 -> 回收结果继续进入项目工作流”的顺滑闭环。
  - 逐步统一“手动 UI 操作”和“Agent 调用”的同源业务逻辑，避免自动化路径与手动路径产生不一致结果。
  - 补齐执行过程可见性、人工确认、失败回退、产物保存和审计日志，让自动化不牺牲可控性。
  - 保留手动模式作为默认可理解入口，并允许用户在关键步骤切回手动编辑。

### 7. Benchmark 与评测体系构建 (Benchmark & Evaluation)
- **核心目标**：建立适配 Ludens-Flow 的评测体系，用可重复、可比较的方式衡量工作流质量、稳定性与真实任务完成度。
- **具体方向**：
  - 构建项目自定义 workflow benchmark，覆盖需求澄清、定稿确认、工件生成、Review 回流、多模态输入与异常场景处理。
  - 参考真实任务型 benchmark 与工具调用 benchmark，评估多 Agent 协作、结构化输出和工具使用质量。
  - 沉淀统一的评估指标，例如阶段推进成功率、误跳转率、工件完整性、响应时延与演示稳定性。

### 8. 桌面安装版与本地应用化 (Desktop App Packaging)
- **核心目标**：在 V3 工作台能力稳定后，将 Ludens-Flow 打包成更适合本地游戏开发场景的桌面应用，而不是长期依赖手动启动 Web/后端服务。
- **具体方向**：
  - 采用 Tauri Shell + Python 后端 Sidecar + 现有 React 前端的路线，尽量保留当前前后端业务结构。
  - 新增 `src-tauri` 桌面壳工程，用 Tauri 管理窗口、图标、菜单、安装包和后续自动更新能力。
  - 将 Python FastAPI 后端作为 sidecar 启动、检测和关闭，避免用户手动运行后端，并处理端口冲突、启动失败和进程清理。
  - 收口前端 API base 配置，使开发态、Web 预览态和桌面产品态可以共用同一套前端代码。
  - 逐步正规化本地配置与数据目录，将 `.env`、workspace、logs、cache 等迁移到系统应用数据目录。
  - 保持工作区路径审核、文件写入权限、MCP 权限和命令执行权限仍由后端统一控制，避免桌面壳绕过既有安全边界。
  - 补齐 Windows 安装包、应用图标、版本号、快捷方式和发布流程，后续再评估 macOS 支持。
